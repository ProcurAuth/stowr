Requirements

  • Docker. The scripts run the compiler in a container. Do not install a compiler on the host.
  • Nothing else for the build. The test stacks (SeaweedFS, MinIO, Garage, Playwright) also run in Docker.

Scripts

ScriptUse
scripts/cargo.sh <arguments>Run cargo in the development image (stowr-dev:1). The script runs as the user of the host. The cargo registry and the target folder are Docker volumes: no file of root appears in the repository.
scripts/static.shBuild the static program for the musl target of the host architecture: x86_64-unknown-linux-musl or aarch64-unknown-linux-musl. --check also checks that the file is static and runs it. --copy <folder> copies the file to a folder of the host.
scripts/check-invariants.shCheck the rules of the runtime that the compiler does not check. Refer to "Rules of the runtime".
scripts/build-site.pyBuild the pages of docs/ from the Markdown files. --check changes nothing and fails when a page is not current. It needs python3 only.
scripts/check-docs.pyCheck the links, the site, the rules of ASD-STE100 and the hygiene of the files. It makes no network request. --online also asks each public URL. It needs python3 only.

The release build reads STOWR_BUILD_VERSION, STOWR_BUILD_COMMIT and STOWR_BUILD_DATE at compile time. stowr version and /api/build show them. A build without them shows dev.

The test images also set STOWR_MULTIPART_COPY_THRESHOLD and STOWR_MULTIPART_COPY_PART_SIZE at compile time: a copy then goes in parts with small objects. A release build does not set them. Refer to ARCHITECTURE.md, "Copy in parts".

Validation

sh
scripts/cargo.sh fmt --all -- --check
scripts/cargo.sh clippy --all-targets --locked -- -D warnings
scripts/cargo.sh test --locked
scripts/check-invariants.sh
scripts/static.sh --check
python3 -I scripts/check-docs.py

Layout of the code

The crate is at the root of the repository: Cargo.toml, build.rs and src/. src/main.rs starts the program. src/lib.rs has one module for each part of the program. Each part is a folder src/<part>/ with its mod.rs.

FolderContent
src/common/The shared types: the error and its envelope, the typed configuration, the context of an operation, the request and the answer. Also the storage traits, the JSON encoder, the times, the query, the embedded interface and the application.
src/config/The reader of the HCL file, the table of the keys, the reference, print-config, the command line, the identity of the build. src/config/env.rs is the only reader of the environment.
src/server/The HTTP server, the route table, the middlewares, the interface, the object gateway, the listing, the copy and the delete.
src/instance/The storage instance: the gates, the budgets, the ceilings, the learned permissions, the versions, the range readers, the signed cursors.
src/provider/The clients of S3 and of GCS, and the shared client of each auth block.
src/volume/The volume back end. It is the only folder that writes to the local file system.
src/uploads/The resumable uploads, the resume token, the incomplete multipart uploads.
src/jobs/The background jobs, Insights, the integrity, the inspection, the version routes.
src/archive/The ZIP reader and writer, the ZIP of a folder, the archive entries, the extraction.
src/lifecycle/The object tags and the lifecycle rules.
src/bucket/Object Lock, the encryption, the edit of the metadata, the usage and the quota.
src/access/The access policy: the routes and their actions, the resource tree, the options route, the guard of the PDP.
src/pv_docs/, src/pv_data/, src/pv_structured/, src/pv_media/The previews and the details of the objects.
src/testkit/The test kit: the memory back end and the shared helpers of the tests.
src/public/The browser interface. build.rs embeds each file in the binary.

Dependencies

Each dependency has an exact version in Cargo.toml, and Cargo.lock fixes the others. Add a dependency only when the code that it replaces is larger or less strict. The program has its own code for these jobs:

  • the HCL reader, the CSV reader and the MIME reader;
  • the ZIP reader and writer, the SQLite reader, the Parquet reader and the DER reader;
  • the readers of image and media headers;
  • the S3 signature.
CrateReason
tokioThe asynchronous runtime. It runs the listener, the timers, the signals, the tasks of the jobs and the threads for the CPU work.
hyper, hyper-util, http, http-body, http-body-util, bytesThe HTTP/1.1 server and the HTTP/1.1 client of the providers, of the admin APIs and of the PDP. The client follows no redirect and uses no proxy.
rustls, tokio-rustls, hyper-rustlsTLS 1.2 and 1.3 to the providers and to the PDP. The roots are the certificate bundle of the image. No environment variable.
aws-lc-rsSHA-256, HMAC-SHA-256, AES-GCM, RSA signatures and the random generator. It is also the cryptography of rustls.
serde, serde_jsonThe JSON of the answers, of the requests and of the provider APIs. src/common/json.rs gives the exact form of the answers.
flate2Deflate, gzip and zlib with the pure Rust back end: the ZIP entries, the gzip answers, the compressed parts of the previews.
quick-xmlThe pull reader of XML: the provider answers, the Office Open XML parts, EPUB and SVG headers. It expands no external entity.
base64The base64 forms of the checksums, of the tokens and of the previews.
libcstatfs, O_NOFOLLOW and the error numbers of the volume back end.
tower-serviceThe connector trait of the provider client: TCP, then TLS, with a time limit for each step.
procurauth-pepThe PEP of ProcurAuth 1.1 for the mode authzen. It checks the identity token, asks the PDP, keeps the answers and gives the transport over TLS. It comes from one fixed commit of the ProcurAuth repository.
procurauth-coreThe shared types of ProcurAuth: the key set of the edge (JWK Set and PEM keys), the JWS decoder and the decision of the PDP. It comes from the same commit as procurauth-pep.

Rules of the runtime

scripts/check-invariants.sh checks these rules. The CI runs it.

  • The program never runs another program.
  • Only src/config/env.rs reads the environment: the variables that the configuration names with _env.
  • The clients of the providers use no proxy and follow no redirect.
  • Only the folder src/volume/ writes to the local file system: the files of a volume block. Put the code of a test that makes fixtures in a file named tests.rs or *_tests.rs.
  • Only src/volume/statfs.rs has unsafe code (unsafe_code is deny for the crate).
  • The repository has no font file.
  • The interface loads nothing from another origin.
  • Each dependency has an exact version.

The compiler and clippy also refuse unwrap, expect, panic!, todo!, unimplemented!, dbg! and the print macros in the code of the program. The tests can use them.

The program keeps no state on the local file system. It runs as a static binary in a scratch container with a read-only root file system. Only the HCL file, the credential files and the folders of the volume blocks are mounted.

Configuration reference

docs/configuration-reference.md comes from the table of the keys in src/config/. After a change of the table, make it again:

sh
scripts/cargo.sh run --quiet -- config-reference > docs/configuration-reference.md

A test fails when the file and the table do not agree.

Documents and website

The Markdown files in docs/ and CHANGELOG.md are the source of the website. scripts/build-site.py makes the pages docs/*.html from them. The Overview page and the page 404 are in the script. The pages have no build step to read, no external request and no web font. They use relative links, so they work from file:// and from GitHub Pages.

After a change of a Markdown file, run the script and commit the pages with the change:

sh
python3 -I scripts/build-site.py
python3 -I scripts/check-docs.py

scripts/check-docs.py runs four checks:

  • the links and the anchors;
  • the pages of the site;
  • the rules of ASD-STE100: sentences of 25 words at most, six sentences in a paragraph, and no banned word;
  • the hygiene of the files: no secret, no address, no e-mail address and no image registry.

The workflow docs runs it.

Frontend

The frontend under src/public is plain HTML, CSS and JavaScript. It has no build step. Edit the files, build the program again and reload. The program embeds one interface: no key selects an interface.

  • Change a colour, a size, a radius or a duration in the tokens at the top of assets/css/stowr.css. The components name tokens only.
  • A new icon name needs a rule in assets/css/icons.css and a Tabler file in assets/icons/tabler/.
  • A test of the server finds an external URL, an absent asset, an absent icon file and an icon name without a rule.

Browser tests of the interface

test/frontend/run.sh starts three S3 providers (SeaweedFS, MinIO and Garage) and Stowr. It puts the test objects in the buckets and in the volume files. It runs browser-tests.js in a Playwright container. Refer to test/README.md. Two runs at the same time on one machine need two project names: set FRONTEND_TEST_PROJECT. To run some tests only, set ONLY to a part of their names.

sh
./test/frontend/run.sh

FUSE test of the volumes

test/volume-fuse/run.sh runs the tests of the volumes and a browser smoke test on a FUSE mount of SeaweedFS (weed mount). Only the container of the mount gets /dev/fuse, SYS_ADMIN and no AppArmor profile. The container has the pinned Rust image, the source and the compiled tests. The script runs cargo test volume:: in it, with the variable STOWR_TEST_VOLUME_DIR set to a folder of the mount. Only the tests (src/volume/tests.rs) read this variable. Without it, the tests use a folder of the temporary folder of the system.

sh
./test/volume-fuse/run.sh

Conformance test of the access policy

test/conformance/run.sh runs the ProcurAuth conformance runner against Stowr in Docker. Set PROCURAUTH_DIR when the ProcurAuth repository is not next to the checkout of Stowr. Refer to CONFORMANCE.md.

sh
./test/conformance/run.sh

Scratch runtime

sh
./test/scratch-runtime.sh

The test builds the scratch image. It checks the numeric user and the identity of the static binary. It starts the container with --read-only and runs the health check of the program.

Release

.github/workflows/release.yaml makes the release when you push a tag vX.Y.Z (or vX.Y.Z-suffix, a prerelease). Do these steps:

  1. Set the version X.Y.Z in Cargo.toml. Run scripts/cargo.sh check without --locked: cargo writes the version into Cargo.lock.
  2. Add the section ## X.Y.Z (date) under ## Unreleased in CHANGELOG.md. The text of this section becomes the notes of the release. Run python3 -I scripts/build-site.py: the pages show the version of Cargo.toml.
  3. Merge the change into main, then tag the commit: git tag vX.Y.Z, git push origin vX.Y.Z.

The workflow does these steps:

  1. It makes sure of three facts. The tag is equal to the version of Cargo.toml. CHANGELOG.md has the section. No workflow publishes a container image.
  2. It runs the format check, clippy, the tests and scripts/check-invariants.sh.
  3. It builds the static binary on an amd64 runner and on an arm64 runner with scripts/static.sh. The compile-time values are the version (X.Y.Z), the commit and the date of the commit. It makes sure that each binary is static, has the correct architecture, and shows the version.
  4. It packs stowr_X.Y.Z_linux_amd64.tar.gz and stowr_X.Y.Z_linux_arm64.tar.gz. Each archive has one file at its root: stowr, mode 0755.
  5. It writes checksums.txt (SHA-256, the format of sha256sum) and creates the GitHub release with the three files.

No workflow builds an image for a registry or publishes an image.

Release validation

Before you distribute an archive, extract that archive into a clean folder and do the full validation there.
