Runtime shape

The application is one static binary. The files of the browser interface are in the binary. The binary needs no shared library and no dynamic loader. It runs no other program and writes no application state to disk. It writes files on the local disk only for a volume block, in the folder of that block (refer to "Volumes").

The runtime can be placed in a scratch container with a read-only root filesystem. Only the HCL file and any credential files need to be mounted read-only.

Configuration and shared provider clients

HCL defines reusable authentication objects and bucket views. Buckets that use the same authentication share the provider credentials, the token refresh state, the HTTP transport and the connection pool. Each bucket independently defines:

  • provider bucket name;
  • display name;
  • virtual root prefix;
  • permission ceiling;
  • navigation scan limit;
  • learned capability state.

Access policy

The access block sets who can use the server. In mode authzen, each route checks the identity token and asks a PDP. The rules, the routes and the resource tree are in ACCESS.md.

Storage interfaces

The backend separates listing, object reads, ranged reads, writes, deletion, copy (also with new metadata), multipart upload, and version operations. Read-only preview code receives only the operations it needs.

All provider traffic passes through:

  • a global concurrency gate;
  • a per-bucket concurrency gate;
  • a request counter;
  • a transferred-byte counter;
  • request cancellation;
  • strict response validation.

Provider redirects and environment-derived proxies are disabled.

Stateless state model

The server has no local database, cache directory, checkpoint directory, or temporary-file contract. A volume is the only exception. An upload to a volume writes a temporary file in the folder of the target (refer to "Volumes").

Process memory contains only bounded live state:

  • at most four active or queued background jobs;
  • a small terminal-job history;
  • current upload sessions;
  • current preview sessions;
  • short-lived range caches;
  • process-local permission observations;
  • short-lived Insights results.

A process restart discards all of this state. No hidden object is written to a connected bucket to replace local state.

Upload resume protocol

A resumable upload creates a provider-side S3 multipart upload or GCS resumable session. The server returns an opaque stowr1 token. The token holds the provider coordinates, the target object, the size, the media type, the chunk size and the expiry. It is encrypted and authenticated.

The token key is derived from the configured provider credential material when available. Thus another process with the same HCL credentials can open the token without a server-side record. The server then reconciles the actual provider state:

  • S3: lists uploaded parts and validates contiguous part numbers and sizes;
  • GCS: queries the resumable-session offset;
  • volume: reads the size of the temporary file of the upload (refer to "Volumes").

The process tracks at most four active upload sessions. Completed and canceled sessions are removed from process memory. Cancel also aborts the provider session when supported.

The browser currently keeps active tokens in page memory. An API client may retain the opaque token outside the server and submit it to /api/uploads/resume after a server restart.

Upload checksums

An S3 upload can carry a SHA-256 checksum. The GCS provider does not use it.

The browser computes the SHA-256 digest of each chunk with crypto.subtle. A page that is not secure has no crypto.subtle. A page is secure with HTTPS or on localhost. Such a page sends no checksum.

The request POST /api/uploads has the field checksum. The value is "" or "sha256". The answer shows the value that the server accepts. With sha256, the server starts the multipart upload with x-amz-checksum-algorithm: SHA256.

Each chunk of such an upload needs the header X-Checksum-Sha256. The value is the base64 digest of the chunk. A chunk without this header gets 400 checksum_required. A value that is not a 32-byte digest gets 400 invalid_checksum.

The server sends the digest to the provider in x-amz-checksum-sha256. The provider refuses a part with other bytes. At the end, the server sends the digest of each part in CompleteMultipartUpload.

The answer has the field checksumVerified. It is true when the provider returned the digest of each part. The server also reads the checksum of the object. This checksum is the SHA-256 of the part digests. S3 writes it as <digest>-<number of parts>.

Garage writes the digest only. A different value makes the upload fail.

A direct upload (PUT /s3) accepts the same header. The browser uses it for a file under 32 MiB. The answer has X-Checksum-Sha256-Verified: true when the provider returned the same digest. A provider that does not store checksums gives no confirmation. The upload still succeeds.

The resume token keeps the algorithm. After a restart, the server reads the digest of each part from the list of parts of the provider.

Object tags and lifecycle

Only the S3 provider has object tags. A provider that does not know them answers 501. The server turns this answer into the error tagging_unsupported. The interface then hides the tag controls. Garage does not support tags. SeaweedFS does.

GET /api/tags?key= gives the tags of an object. PUT /api/tags replaces the whole set. An empty set removes all tags. The server checks the limits of S3 before it sends the request.

An object has at most 10 tags. A key has 1 to 128 characters and does not start with aws:. A value has at most 256 characters. A tag has letters, digits, spaces and + - = . _ : / @ only.

POST /api/tags/bulk starts the job tag_prefix. The body has prefix, add (tags to set) and remove (keys to remove). The job reads the tags of each object under the prefix. It writes them again only when the result is different. An object that would have more than 10 tags stops the job with its key in the message.

At start, the server probes each instance with a tag read on a key that does not exist. A provider with tags answers "no such key". A provider without tags answers 501 or 405. The instance then reports tagsSupported: false in /api/instances. A denied or slow probe does not show that the feature is absent.

The page hides the tag controls from the first load and sends no tag with an upload. Garage accepts x-amz-tagging and drops the tags without a word. Thus the server refuses an upload with tags for an instance without tags. It answers 501 with tagging_unsupported.

An upload can carry tags. A direct upload takes the header X-Amz-Tagging (a query string such as a=b&c=d). POST /api/uploads takes the field tags. The server sends them to the provider in x-amz-tagging.

In a bucket with versioning, a tag request names the version of the object. The server reads it with a HEAD request. It is null for an object made before the versioning. SeaweedFS takes more than 10 seconds to read the tags of such an object when no version is named. A request that has version uses it as it is.

GET /api/lifecycle gives the lifecycle rules of the bucket in rules. A bucket without rules gives an empty list. The details of a file use the rules to tell what happens to the object, also for tags that the person did not save yet. The answer also has the state of the editor of the rules. Refer to Edit of the lifecycle rules.

The listing of the provider does not give tags, and S3 has no request that lists objects by tag. The tag column and the tag filter read the tags of the files on the page. They are in the settings of the listing, behind the gear. The tag column is on by default, and the tag filter is off. They read 4 files at the same time and at most 100. The tag filter hides rows of this page only.

Versions in the interface

The details of a file have a picker of versions. It shows each version with its number (v1 is the oldest), its date, its size and the change of size since the version before. A choice opens the details of that version. The tags of an older version are read only.

The picker sorts the versions by date, the newest first. In S3, the current version is the newest version that holds data, so the picker shows no text "Current" or "Older". A small dot of the accent colour marks the version that the provider gives with IsLatest, with the tooltip "Current". The dot is the first column of the menu, and the first element of the button for the current version. Two versions with the same date (SeaweedFS gives the date to the second) put the current version first. When the current version is a delete marker, no version gets the dot.

Each row of the picker also has frameless icon buttons: Download, Restore and Delete. They show on hover and on keyboard focus. Restore is not on the current version and needs the write permission. Delete needs the delete permission.

Restore and Delete open a confirmation first. They call POST /api/versions/restore or DELETE /api/versions. A delete that a lock refuses shows the message of 409 object_locked. After a restore or a delete, the details open again. The preview page reads the versions and the preview again. The listing reads its folder again.

A row of the picker is a div with the role option. It has a button for the choice and the action buttons. Up and Down go from row to row. Left and Right go from the choice to the action buttons of the row. Tab goes through every button of the menu, and Escape closes it. The pickers From and To of a comparison have no action buttons.

The picker does not list the delete markers. When the current version of an object is a delete marker, the listing does not show the object, so the page cannot open its versions. This is an old limit.

The comparison of two versions runs in the browser, in the preview page and not in a dialog. The address has the parameter compare (the older version) and the parameter version (the other version). The comparison takes the place of the preview. The browser back button and the button "Back to the preview" show the preview again.

The picker of the versions of the preview stays in its place and becomes the version To. The version From appears at its left, and the statistics of the change are between the two. The header gets no new row. A button closes the comparison. The picker of versions opens this address.

The page reads each version with GET /s3?key=&version=. It does not read a version larger than 2 MiB. A version with a NUL byte, or with a text that is not UTF-8, is not text. The page says so, and it offers the comparison of the bytes.

The page picks the view from the extension of the key. The two versions show side by side by default. Other views are the unified list and the patch of git.

  • Text: a diff of lines (Myers), with 3 lines of context. The changed words show in a changed line. A side that has no line shows hatched. A fold hides the unchanged lines, and a click shows them.

  • JSON: the modes of the preview. Raw shows the text as stored. Beautify shows the indented text, with an option to sort the keys. Tree shows the paths with their state (added, removed, changed). A branch with a change is open, and a click opens the other branches.

    The format and the order of the keys are not changes. A version that is not JSON uses the text views.

  • CSV, TSV and PSV: two tables side by side, or one table. The view shows the rows that were added, removed or modified, and the cells that changed. A removed row and an added row are one modified row when they have the same first cell, or most cells equal.
  • Patch: the patch in the unified format of git, with diff --git, index, ---, +++, the hunks @@ and the line \ No newline at end of file. It applies with git apply and patch -p1. The buttons copy it or download it as <name>.patch.

The last line of a text with no line break is not the same line as the same text with a break, as in git.

The picker of versions is also in the bar of the preview page, with the same actions. It replaces the list of versions there, and the action "Versions" of the menus. The badge with the count in the listing opens the details of the file, with the picker. The page has no table of the versions.

A diff that needs more than 2500 edits shows as a replacement of the lines. The algorithms are in assets/js/diff.js. They have no DOM, and test/frontend/diff-tests.js tests them in Node.

Background jobs

Jobs are memory-only and use two workers. The manager admits no more than four active or queued jobs. Terminal results are retained only up to job_history_limit.

Supported job types are limited to operations that can stream with bounded memory:

  • prefix copy, move, and delete;
  • copy or move of one object in parts (copy_object, move_object);
  • Insights statistics;
  • per-object integrity verification;
  • selected archive-entry extraction;
  • selected archive-entry integrity verification;
  • abort of the incomplete multipart uploads older than a number of days (abort_multiparts).

Insights uses a 100 ms synchronous fast path. A fresh completed result can be reused for 30 seconds. Longer work continues in memory and can be paused, resumed, or canceled while the process remains alive.

A job that deletes a prefix deletes the objects in batches of 1000 keys. It uses DeleteObjects of S3. The same applies to the deletion of the sources in a move of a prefix. The job counts a batch only after the provider deleted it. After a pause or a stop, the job continues after the last deleted key.

A provider that refuses DeleteObjects with 501 or 405 gets one request for each key. The server remembers this refusal. A key with a character that XML cannot carry always gets its own request. The GCS provider has no batch delete.

A key that an active Object Lock keeps does not stop a delete job or a move job. The job counts it in locked, keeps the first 20 keys in lockedKeys, and continues. Such a key is not in processed for a delete. The source of a move stays, and its copy exists. Refer to Object Lock.

Copy in parts

CopyObject of S3 refuses a source above 5 GiB. Thus a copy, a move, a rename and the restore of a version use a copy in parts from a threshold up. The threshold is 5 GiB minus 256 MiB. The engine is in the S3 backend (src/provider/s3/copy.rs), behind the optional trait MultipartCopier of the backend. The GCS backend does not have it: its copy has no such limit.

The engine does these steps:

  1. It reads the source with HEAD, with versionId when the copy names a version. It gets the size, the ETag and the headers.
  2. It reads the tags of the source. A source with x-amz-tagging-count: 0 needs no request. A provider without tags (501 or 405) gives no tag.
  3. It sends CreateMultipartUpload with Content-Type, Cache-Control, Content-Disposition, Content-Encoding, Content-Language, Expires, the x-amz-meta-* headers and x-amz-tagging.
  4. It sends one UploadPartCopy for each part of 256 MiB, with x-amz-copy-source-range. Four parts go at the same time. Above 10000 parts, the parts become larger.
  5. It sends CompleteMultipartUpload.

Each part has x-amz-copy-source-if-match with the ETag of the source. A source that changes during the copy makes the copy fail. On an error or a cancel, the engine sends AbortMultipartUpload. The abort has its own time limit of 30 seconds, because the context of the copy can be canceled. No byte of the object goes through Stowr.

Each request of the engine takes a slot of the concurrency gates of the bucket. Thus the limits max_concurrent_requests_per_storage and max_concurrent_storage_requests apply. A request of the engine waits for its slot with no time limit.

The engine has an options structure. It holds the source version, the new metadata, the new tags, other headers of CreateMultipartUpload, the ETag that the caller read, and a progress function. When the options give an ETag, a source with another ETag stops the copy with 412 before the upload starts. The metadata edit uses the same engine with new metadata.

POST /api/copy and POST /api/rename of one object first read its size with HEAD. Under the threshold, the copy stays one synchronous CopyObject request, and the answer is 200. From the threshold up, the answer is 202 with a job copy_object or move_object.

The job has totalBytes, the size of the source, and copiedBytes, which grows after each copied part. A move deletes the source after the copy. A pause or a cancel aborts the multipart upload. A resume starts the copy again from the first part. The jobs of one object use the background request budget (max_background_storage_requests).

A prefix copy and a prefix move use the size of each object in the listing. An object from the threshold up goes in parts. The job counts copiedBytes, with the parts of the object in progress.

The restore of a version from the threshold up uses the engine with the version as the source. It stays one synchronous request.

The threshold and the part size are values of the program. The unit tests change them. The test image sets them at compile time with the variables STOWR_MULTIPART_COPY_THRESHOLD and STOWR_MULTIPART_COPY_PART_SIZE. The Docker build arguments MULTIPART_COPY_THRESHOLD and MULTIPART_COPY_PART_SIZE of test/browser/Dockerfile give them.

These are not configuration keys. A release build does not set them. A value that is not an integer in its range stops the program at start. The threshold is 1 byte to 5 GiB. The part size is 5 MiB to 5 GiB. The log shows each value that the build changed.

Edit of the metadata

GET /api/metadata?key=&version= gives the stored metadata of an object, or of one version. These are the standard headers Content-Type, Cache-Control, Content-Disposition, Content-Encoding, Content-Language and Expires, and the user metadata (x-amz-meta-*). The server reads them with a HEAD request to the provider. The gateway /s3 puts private, no-store in front of the Cache-Control of the provider, so the page does not read the values from the gateway. The answer also has etag, lastModified, version, size, multipartETag (the ETag has the form <digest>-<parts>), copyInParts (the save copies the object in parts) and maxMetadataBytes.

PUT /api/metadata replaces the metadata. The body has key, version (optional), etag and lastModified (the values that the form read), headers and metadata (a list of key and value). The body gives the complete state: a header or a user metadata that the body does not give is removed. The answer is the new state of the current object. The server checks each value before it sends a request:

  • The six headers are a closed set. An unknown field in headers or in the body gives 400 invalid_json.

  • Each value has 1 to 1024 printable ASCII characters, with no space at the start or the end. The standard headers have more rules. Content-Type is a media type. Content-Disposition is inline or attachment with parameters.

    Content-Encoding and Content-Language are lists of tokens. Cache-Control is a list of directives. Expires is an HTTP date in GMT.

  • A user metadata key has lowercase letters, digits, ., _ and -, and starts with a letter or a digit. Each key is unique. A value has printable ASCII characters and is not empty. The keys and the values have 2048 bytes at most in total, as in S3.

A wrong value gives 400 invalid_metadata with the name of the field. The server then does these steps:

  1. It reads the object (or the version) with HEAD. An ETag or a modification date that is not the value of the form gives 412 object_changed. SeaweedFS, MinIO and Garage keep the ETag when only the metadata changes, so the date is necessary.
  2. Under the threshold of the copy in parts, it sends CopyObject onto the same key. The request has x-amz-metadata-directive: REPLACE, x-amz-tagging-directive: COPY and x-amz-copy-source-if-match with the ETag of the form. A provider answer 412 also gives 412 object_changed.
  3. From the threshold up, it uses the engine of the copy in parts. The engine gets the new metadata at CreateMultipartUpload, the tags of the source and the ETag of the form.

The copy also sends the storage class, the website redirect and the server-side encryption of the source again, when the HEAD answer has them. Else AWS would change them. An object with an encryption key of the customer (SSE-C) gives 400: Stowr does not have the key.

A request with version copies that version onto the key. The version becomes the current version, as a restore does. The tags of that version stay.

The copy needs the write permission of the instance. No new permission exists.

The form is a grid of labels and fields. Each field has the width of its value, and 100% at most on a narrow window. BB.suggest (assets/js/common/suggest.js) adds the suggestions to a text field with the ARIA combobox pattern. The popover is in the large window, with the look of the menu of the version picker.

The typed text filters the values, and a free value stays possible. Down and Up move the mark, Enter chooses, and Escape closes the popover and not the window. The first value of Content-Type is the type that detect.js guesses from the name.

At start, the server probes each instance that has the write permission. The probe is a copy with REPLACE of an object that does not exist, with an ETag that no object has. A provider with CopyObject answers "no such key" and writes nothing. A provider without it answers 501 or 405.

The instance then reports metadataEditSupported: false in /api/instances. A later 501 of an edit has the same effect. The GCS backend has no edit. It answers 501 metadata_unsupported, and the page hides the button.

Cleanup of incomplete multipart uploads

An incomplete multipart upload keeps its parts on the provider until a person completes it or aborts it. The parts use storage, but no listing shows them. The code is in src/uploads/, behind the optional trait MultipartUploadLister of the backend.

GET /api/multiparts?prefix=&max=&token= gives the incomplete uploads under prefix. The answer has uploads, nextToken, now (the clock of the server), minimumAbortAgeHours and partsPageSize. Each upload has key, uploadId, initiated, parts, bytes, partsAtLeast, partsUnknown and active. max is from 1 to 500, and the default is 100. Another value gives 400 invalid_multipart_request.

The server reads the list with these rules:

  • It sends ListMultipartUploads with no prefix. MinIO gives an empty list for a prefix that is not a full key. The server keeps the uploads under the root prefix of the instance and under prefix.
  • It sends the next request with the markers that the provider sent, as the provider sent them. SeaweedFS sends only NextUploadIdMarker. Garage and AWS send NextKeyMarker and NextUploadIdMarker. MinIO ignores max-uploads and sends all the uploads in one page.
  • nextToken has the markers and a position in the page. Thus the next answer can start in the middle of a page that has more uploads than the request asked for.
  • One answer reads 10 pages of the provider at most. A provider that sends the same markers again gives 502 provider_paging, not a loop.
  • For each upload, the server sends one ListParts with max-parts=1000, four at the same time. An upload with more parts gets partsAtLeast: true: the count and the size are those of the first 1000 parts. An upload that the provider no longer knows (404 NoSuchUpload) is not in the answer.

initiated is the Initiated date of the provider. SeaweedFS gives no date. The page then shows "unknown" for the start and the age.

POST /api/multiparts/abort has two forms. The body gives one of them. Both forms, or none, give 400 invalid_multipart_request.

  • uploads, a list of 1 to 1000 key and uploadId, aborts each upload at any age. The page asks for a confirmation first. The answer is 200 with aborted, skipped and failed. An upload that the provider no longer knows counts as aborted.
  • olderThanDays (1 to 36500) and prefix start the job abort_multiparts. The answer is 202 with the job. The job reads the whole list and aborts each upload under prefix that started before the cutoff. The cutoff is the time of the request minus olderThanDays days. A resumed job uses the same cutoff.

The job counts aborted, skippedUndated, skippedRecent, skippedActive and failed in multipartAbort. These safety rules apply:

  • The job never aborts an upload without a start date. The provider does not let Stowr know its age.
  • The job never aborts an upload younger than 24 hours, also when the cutoff is later.
  • No request aborts an upload that the resumable-upload store of this process sends now (status uploading, src/uploads/). The list shows such an upload with active: true.

GET /api/multiparts needs the read permission of the instance. An abort needs the read and the write permissions.

At start, the server sends ListMultipartUploads with max-uploads=1 to each instance that has the read permission. A provider that answers 501 or 405 gets multipartUploadsSupported: false in /api/instances, and the page hides the item. The GCS backend has no list: it answers 501 multipart_unsupported.

The item "Incomplete uploads" of the Actions menu opens a large window for the current folder, or for the bucket at the root. The window has a table with the key, the start, the parts, the size and the age of each upload. Each row has a checkbox and a frameless abort button. The window also has "Abort selected" and "Abort everything older than N days" (N is 1 by default). The window tells how many uploads have no start date.

A person without the write permission sees the list with no abort control. A note tells that a lifecycle rule can abort the incomplete uploads. Its link opens the part "Lifecycle rules" of the information page. Refer to Edit of the lifecycle rules.

Edit of the lifecycle rules

PutBucketLifecycleConfiguration replaces the whole configuration of a bucket. The providers do not keep the same settings, and some drop a setting without an error. The code is in src/lifecycle/, behind the optional trait BucketRules of the backend. The GCS backend has no lifecycle rules: it answers 501 lifecycle_unsupported.

The state of the editor

GET /api/lifecycle gives editor next to rules. editor has these fields:

  • hash: the SHA-256 of the configuration as the provider sent it, and of the indexes of the editable rules. A rule that becomes "kept as is" thus also changes the hash.
  • entries: one entry for each rule, in the order of rules. An editable entry has rule. Each other entry has xml (the bytes of the rule) and reason.
  • fields and hidden: the fields that the editor offers, and the reason for each other field.
  • provider, providerNote, versioning, rootPrefix, writable, readOnlyReason, maxDays (36500) and maxRules (1000).

A rule is editable when it has an ID and only these elements:

  • Status;
  • a Filter with a Prefix, one Tag, or an And with a Prefix and one Tag;
  • an Expiration with Days, or with ExpiredObjectDeleteMarker;
  • a NoncurrentVersionExpiration with NoncurrentDays, and an AbortIncompleteMultipartUpload.

Each field of the rule must also be offered for the instance. For an instance with a root prefix, the prefix of the rule must start with the root prefix. The editor shows the prefix after the root prefix, and the server adds the root prefix again. Thus a new rule of such an instance never applies to the whole bucket.

The editor keeps each other rule as is. Such a rule has one of these parts:

  • a transition, an expiration on a date, or a size filter;
  • a filter with two tags or more;
  • the old Prefix element outside of Filter, NewerNoncurrentVersions, or an XML attribute.

The editor also keeps a text with spaces at its start or end. It keeps a tag key with = or ,, and a tag value with ,. The form cannot show them exactly.

The window shows such a rule as a read-only row with the note "Kept as is", the reason and its XML. For an instance with a root prefix, a rule outside of the root prefix shows no XML and no filter. It belongs to another part of the bucket.

The save

PUT /api/lifecycle has instance, hash and rules, the complete list of the editable rules. Each rule has id, enabled, prefix, tag, expirationDays, noncurrentDays, abortMultipartDays and expiredDeleteMarker. A zero number of days means "no such action". The server does these steps under a lock of the instance:

  1. It reads the configuration again and compares its hash with hash. A different hash gives 409 lifecycle_changed. The page then offers "Reload the rules".
  2. It checks the rules. A refusal gives 400 invalid_lifecycle, or 400 lifecycle_field_unsupported for a field that the editor does not offer.
  3. It writes the document. The document has the start tag of the root as the provider sent it. Then it has the editable rules. Last, it has each other element of the root with its bytes. An editable rule that the save does not change also keeps its bytes.
  4. It reads the configuration again and compares each rule with the rule that it sent.

The checks of step 2 are the limits of S3 and of AWS:

  • A bucket has 1000 rules at most. An ID has 1 to 255 characters, and no other rule has the same ID. MinIO refuses two rules with one ID.
  • A number of days is from 1 to 36500. A rule has one action or more.
  • A rule cannot have Days and ExpiredObjectDeleteMarker in one Expiration.
  • A rule with a tag filter cannot abort incomplete uploads or remove delete markers. AWS refuses these rules.
  • A tag follows the rules of the object tags.

MinIO and Garage refuse a configuration without a rule. When no element stays, the server sends DeleteBucketLifecycle in place of the write.

The comparison of step 4 ignores the spaces, the namespaces and the order of the children, because MinIO changes the order in And. A rule without an ID matches a rule with the same content, because MinIO gives an ID to such a rule.

For each difference, the answer has a sentence in warnings, for example "The storage provider dropped the tag filter retention=30d of the rule "logs". The rule now applies to every object under logs/". The server restores nothing. The page shows the sentences and the rules as the provider keeps them. Then this process does not offer the dropped field again for the instance.

A refusal of the write by the provider gives these answers:

  • 403 gives 403 lifecycle_write_denied. 501 or 405 gives 501 lifecycle_write_unsupported. The editor of the instance is then read only, with the reason, until a later write works.
  • Another 4xx gives 400 lifecycle_refused. The rules of the bucket do not change.

When the read of step 4 fails, the answer is 200 with a sentence in warnings and no editor. The rules are saved, and the page reads them again.

S3 has no condition on PutBucketLifecycleConfiguration. The lock and the hash stop a save over a change of another window of this process, or over a change before the save. A change by another S3 client between the check and the write is lost.

Object Lock

Object Lock keeps one version of an object: a legal hold, or a retention until a date. The code is in src/bucket/object_lock.rs, behind the optional trait ObjectLockManager of the backend. A bucket gets Object Lock only at its creation, and such a bucket always keeps versions. Each lock applies to one version.

Detection

At start, the server reads GetObjectLockConfiguration of each instance with the read permission. The request is a read. Only the answer ObjectLockEnabled: Enabled gives objectLockSupported: true in /api/instances. These answers give false, and the page shows nothing of Object Lock:

  • a bucket without Object Lock: 404 ObjectLockConfigurationNotFoundError on SeaweedFS and MinIO;
  • a provider without Object Lock: 501 NotImplemented on Garage, or 405;
  • any other failure, for example a refusal or a timeout. The instance then hides the feature until the next start.

The GCS backend has no Object Lock: the routes answer 501 object_lock_unsupported.

Read

Deletes that a lock refuses

The providers refuse the delete of a locked version with different answers. SeaweedFS gives 403 AccessDenied. MinIO gives 400 InvalidRequest with the message "Object is WORM protected and cannot be overwritten". DeleteObjects gives the same codes for each refused key, in the XML body of a 200 answer.

The status alone does not tell a lock from a permission that the person lacks. Thus, after a refusal with one of these codes, the server reads the lock of the version. Only a legal hold or an active retention makes the error 409 object_locked. Its message names the lock and tells what the person can do. Any other refusal stays the error of the provider.

A refusal for a lock does not change the delete permission that the instance reports. A delete without a version id is not refused on SeaweedFS and MinIO. The provider writes a delete marker, and the locked version stays. This is the correct behaviour of S3.

Thus, on a bucket with objectLockSupported, the confirmation of a delete has a sentence about the lock. The delete is of a file or of a folder. The sentence is "This bucket has Object Lock. Encryption

The code is in src/bucket/encryption.rs. Stowr shows the server-side encryption that the provider reports. It can also ask for SSE-S3 for each object that it writes. It does not support SSE-C or SSE-KMS for the writes. It never shows, asks for or keeps a key of the client.

Encryption of the writes

The key encryption of a bucket block is "" (the default) or "sse-s3". Any other value stops the start, and the error says that SSE-C and SSE-KMS are not supported. A gcs bucket with "sse-s3" stops the start: the GCS API has no such header. Refer to configuration-reference.md.

Cost and safety

  • The server makes an admin request only for an instance whose auth block has a usage block. The probe at start makes no admin request.
  • Each request is a GET. One read has a time limit of 5 seconds for all its requests. Each answer has a size limit. The limit is 1 MiB for Garage and for the filer, 16 MiB for /vol/status and datausageinfo, and 64 KiB for the quota of MinIO.
  • The server keeps the result of each instance for 60 seconds, and a failure for 10 seconds. One read at a time runs for an instance: the other requests wait for its result. The read does not stop when the request that started it stops.
  • fresh=1 reads again a result that is older than 10 seconds. The page sends it after a change and after a click on the reload icon.
  • The token and the URLs of the admin API never go into an answer or into a log line. An error names the step and the HTTP status only. print-config and the effective configuration in the log show the URLs and hide the token.
  • A failure does not break the page. The usage of the bucket selector shows no number, and the information page gives the reason.
  • At start, the server compares the source with the provider that the lifecycle probe found. A different known provider gives a warning in the log. The source of the file applies.

Route

GET /api/usage?instance=<id>[&fresh=1] needs the read permission of the instance. /api/instances gives usageSupported for each instance. The answer has these forms:

  • An instance without a usage block: {"supported": false}.
  • A read that works: supported and available are true. The answer also has instance, bucket, rootPrefix, source and usedBytes. It has usedObjects (-1 when unknown), limitBytes and limitObjects (0 is no limit). It has limitSource, approximate, approximateReason, asOf, percent and level.
  • A read that fails: 200 with available: false and error (code usage_unavailable and message). An answer 502 would tell the page that the server does not answer.
  • The capacity of the storage, when the reader gives it. The member storage has scope (cluster, disks or filesystem), usedBytes, totalBytes, freeBytes, percent, level, approximate, approximateReason, note and asOf. A failed read of it gives storageError (code storage_unavailable), and the part of the bucket stays.
  • A volume also gives selfBytes (the size of its files) and selfState. The state is computing while the count runs (at least selfBytes), partial when the count stopped at its budget (at least selfBytes), or ready. Refer to "Volumes".

limitSource is provider, config or "". The key quota_bytes of a bucket block gives the limit when the source gives no byte limit. The server does not enforce this limit.

quotaPercent is the used part of the quota in percent, with one decimal. The server cuts the next decimals: 99.99 % gives 99.9. With a byte limit and an object limit, the larger part applies. quotaLevel is "" without a limit, ok, warning from 80 %, and error from 95 %. storage.percent and storage.level are the same values for the storage.

percent and level come from the part that sets the stronger limit: the quota or the storage, the part with the larger percent. constraint names it: quota, storage, or "" when the answer has no limit. An equal percent keeps the quota. The colour of the bar, the short text of the chip and the warning of a full bucket follow percent.

Volumes

A volume block shows a folder of the server as the browser shows a bucket. The folder can be a Docker volume, an NFS or CephFS mount, or a FUSE mount such as weed mount of SeaweedFS. The server reads and writes the files with the system calls of its process, under the identity of the process.

The code is in the folder src/volume/. This folder has the only code of the program that writes to the local file system. scripts/check-invariants.sh checks it in the CI (refer to DEVELOPMENT.md). The configuration is in CONFIGURATION.md, section "Volume block". The test with a real weed mount is in test/README.md.

Instance and address

  • A volume is a storage instance with the provider fs. /api/instances gives it with "provider": "fs" and "host": "volume". The address of a volume in the interface is /-/volume/<id>/.
  • The labels of the bucket blocks and of the volume blocks are one set of ids: two blocks with the same label stop the start. An auth block with the label volume stops the start when the file has a volume block, because the two addresses would be the same.
  • The list of the interface gives the buckets first, then the volumes, each in the order of the file.

Checks at start

  • path must be absolute, without / at the end and without an empty, . or .. part. The folder must exist, and the process must read it. print-config does these checks too.
  • root_prefix must be a relative folder path that ends with /. The folder must exist in path. The root of the volume is then path/root_prefix, after the symbolic links.
  • When the server can change the files, the start makes and removes a temporary file in the root. This case applies when the permissions include write or delete, or when the block has no permissions. A folder that the process cannot write stops the start. Give permissions = ["read"] for a folder that is read only. server.access_mode = "force_read_only" makes no such check.

Keys and paths

  • A key is a path relative to the root of the volume. The server refuses a key with an empty, . or .. part, a NUL byte, or a part of more than 255 bytes (400 invalid_key).
  • The server resolves each part of a path, one after the other. With access.mode = "open", a symbolic link to a place inside the root is followed. A symbolic link that leaves the root, or that does not resolve, stops the operation with 403 volume_link_refused. The listing with a delimiter shows such a link as an entry with "unreadable": true. The interface shows it with a ban icon and no action. A delete of such a link is also refused.

  • With access.mode = "authzen", the server follows no symbolic link in the path of a key, also a link to a place inside the root. The access policy gives a grant on a folder by the key of the object, not by its real path. A link from one folder to another folder would let a person read the other folder.

    Each link in the path of a key gives 403 volume_link_refused, and the list of a folder shows it as an unreadable entry. The server opens the last part of a file for a read or a copy with O_NOFOLLOW. The server resolves path and root_prefix one time at start. A link there is not a link of a key. Refer to ACCESS.md, "Volumes and symbolic links".

  • A file that is not a regular file (a device, a socket, a pipe) is also unreadable. The server never opens it.
  • Hidden files (a name that starts with .) are visible. The names keep the case that the file system gives.
  • A name that is not valid UTF-8 shows with the replacement character. The server cannot read, write or delete it. A key of a write must be valid UTF-8.
  • The names that start with .stowr-tmp- are for the temporary files of Stowr. A write with such a name is refused, and the listings do not show these files.
  • Limit: a process outside Stowr that changes a symbolic link between the check and the use of a path can race the check. The API of Stowr cannot make a symbolic link.

Listing

  • With the delimiter /, the server reads one folder. The subfolders are the prefixes, also an empty folder and, with access.mode = "open", a symbolic link to a folder of the root. With access.mode = "authzen", such a link is an unreadable entry. The other entries are the objects.
  • Without a delimiter, the server reads the tree. It gives the files, and each empty folder as the key <folder>/ with size 0 (as the folder objects of S3). It does not follow a symbolic link to a folder, because a link can make a loop.
  • The order is the order of the keys of S3 (bytes of UTF-8). The page token is the last key of the page. A token stays valid when the folder changes: the next page starts after that key.
  • A page has 1000 keys at most. max_scan_pages of the block combines pages as for a bucket.
  • A folder with more than 250000 entries gives 422 volume_folder_too_large: the server reads and sorts each folder of a listing in memory.
  • The size and the date of a file come from stat. The content type comes from the extension of the name.

Reads

  • The ETag of a file is the weak validator W/"<size>-<modification time in nanoseconds>". A file has no MD5.
  • HEAD and GET give Content-Length, Content-Type, ETag, Last-Modified and Accept-Ranges: bytes.
  • One byte range gives 206 with Content-Range. A range after the end gives 416. A Range header that is not one valid byte range gives the whole file, as RFC 9110 lets a server do. An empty file has no range.
  • If-Match and If-Unmodified-Since give 412. If-None-Match and If-Modified-Since give 304. The comparison of an ETag is weak. An If-Range with an ETag never matches, because the ETag is weak: the answer is the whole file. An If-Range with a date compares the date to the second.
  • The range readers of the previews send If-Match with the ETag of the file. A file that changes during a preview thus gives 412, as an object of S3.
  • The previews, the Insights, the search, the integrity check and the ZIP download read a volume through the same interface as a bucket.

Writes

  • A write of a file goes to a new temporary file .stowr-tmp-<random> in the folder of the target. The server writes the bytes, synchronizes the file to the disk (fsync), and gives it the name of the target with one rename. A reader sees the old file or the new file, never a part. The write replaces a file that is already there. A folder with the name of the target stops the write (409 volume_folder_exists).
  • A write with the header X-Checksum-Sha256 compares the SHA-256 of the received bytes with the digest of the client. A different digest stops the write (400 bad_digest), and the target does not change.
  • A write makes the folders of the path that do not exist. A part of the path that is a file stops the write (409).
  • With access.mode = "open", a write through a symbolic link to a file of the root writes the target file. The link stays. With access.mode = "authzen", this write gives 403 volume_link_refused.
  • A key that ends with / and has no content makes a folder (mkdir). The Actions menu of the interface has the item "New folder" for a volume.
  • A delete of a file removes the file. A delete of a folder key (<folder>/) removes the folder when it is empty. A key that does not exist, and a folder that is not empty, give no error: a delete of S3 does the same.
  • A copy reads the source and writes the destination as a write of a file. From the threshold of the copy in parts up (refer to "Copy in parts"), the copy is a job. The job shows the copied bytes and can stop.
  • A move and a rename of a file are one rename. A rename to an other file system (EXDEV) copies the file and removes the source. A move of a folder moves each file with one rename, then removes the folders that it emptied.
  • A delete of a folder (the job delete_prefix) deletes the files of the tree, then removes the empty folders from the bottom. A folder that keeps a file (for example a symbolic link that leaves the root) stays.
  • A full file system gives 507 volume_full. A read-only file system gives 403 volume_read_only.

Uploads and incomplete uploads

  • A resumable upload (/api/uploads) writes its chunks to a temporary file in the folder of the target: .stowr-tmp-<random>-<name of the target>. The next chunk starts at the size of the temporary file, so a client can resume after a lost connection. The last chunk synchronizes the file and gives it the name of the target.
  • The resume token holds the path of the temporary file and the key of the target, encrypted and authenticated. A volume has no credential: the key of the token is a random key of the process. Thus a token does not stay valid after a restart of the server. The temporary file stays.
  • The window "Incomplete uploads" lists the temporary files of the volume. It shows the key of the target, the last write to the file (as the date) and its size. The abort of an upload removes its temporary file. The abort by age keeps a file younger than 24 hours. No abort touches a file of an upload that this process sends now.
  • One page of this list reads at most 20000 entries of the tree. The list does not follow a symbolic link.

Functions of S3 that a volume does not have

A volume has no versions, no tags, no metadata of S3, no lifecycle rules, no Object Lock and no encryption of S3. The backend does not have these interfaces, so the server answers 501 to their routes. /api/instances gives false for versioningSupported, tagsSupported, metadataEditSupported, lifecycleSupported, objectLockSupported and bucketEncryptionSupported. The interface hides their controls, and reads no HEAD for the marks of the listing.

Usage

GET /api/usage of a volume (source statfs) has two parts:

  • What the volume holds: selfBytes (also usedBytes) is the sum of the sizes of the regular files of the folder. usedObjects is the number of these files. A sizer counts them in the background. A request never walks the tree, and one walk at a time runs.

    A walk reads at most 1,000,000 entries in 20 seconds. A larger tree gives selfState: "partial". While a walk runs, the answer gives its progress with selfState: "computing". A walk does not follow a symbolic link, and it does not count the temporary files of Stowr.

    The count stays for 5 minutes. A write of Stowr in the volume makes it old, and the next read starts a new walk. A write is an upload, a copy, a move or a delete. A change that a process outside Stowr makes shows after the 5 minutes. The sizes are the sizes of the files, not the blocks of the disk.

  • The storage: the file system of the folder (statfs, scope filesystem). The used bytes are the size minus the available bytes, the total is the size, and the free bytes are the available bytes. storage.approximate is true on a FUSE, NFS, CephFS, SMB 2 or CIFS file system (the type of the answer of statfs). Such a file system can count the used bytes with a delay. The numbers are for the whole file system, also for the other folders on it. A size of 0 (weed mount gave it once, after a delete) gives storageError.

A volume has no quota: the storage is its limit, and the warning applies from 90 % of the file system. The server reads a volume at each request, without the cache: a read is a statfs call and the count in memory.

File systems

  • The server needs a file system with rename in a folder, fsync, and O_EXCL. A hard link (for the archive extraction that must not replace a file) is optional: without it, the server checks the target and renames.
  • The test with a real weed mount of SeaweedFS 4.41 (test/volume-fuse) runs the unit tests of the volumes and a browser smoke test on the mount. The facts of that test are in test/README.md.
  • A network file system can show a change of an other client with a delay. A listing can then be old by a few seconds. The writes of Stowr through the same mount are visible at once.

Insights treemap normalization

The statistics worker builds the semantic treemap on the backend after the complete Insights scan finishes. The backend:

  • calculates the exact global one-percent byte threshold with integer arithmetic;
  • groups sub-threshold direct children into exact Others aggregates;
  • preserves exact bytes and object counts for every emitted node;
  • contracts folder chains that contain only one child and therefore introduce no real branch;
  • removes a sole Others child because the parent already represents the same exact scope;
  • returns an immutable treemap tree plus treemapThresholdBytes.

The browser does only these jobs: the geometric squarified layout, the fit of the labels, the focus feedback and the navigation. It does not rebuild folders, regroup data or decide which single-child nodes to remove.

The browser chooses the label colour of a file tile from the WCAG contrast. It uses black or white text, the colour with the higher ratio on the colour of the tile. That ratio is always 4.5 or more. The tile "Others" has a light tint of the warning colour. Its label has the colour of the text of the theme.

The subtitle of the window gives the path, the count of objects, the total size and the time of the scan: <path> · N objects · SIZE · computed in N ms. The overview fits in the window with no scrollbar at 1280x720 and larger. The lists "Most recent files" and "Largest files" have 10 rows at most. They share the height that is left, and each list scrolls when it is too short. A very small window scrolls.

Version capability and version access

At start, each bucket gets one bounded probe for the list of versions. A successful answer of the provider turns on the version controls. These cases turn them off for that bucket: HTTP 501, a denial, a time-out, a malformed answer and any other error. The start of the application never fails because of the probe.

When available:

  • /api/versions pages exact versions or generations of one key;
  • /api/version-counts counts exact non-delete-marker versions for visible keys;
  • object, metadata, preview, inspection, and integrity endpoints accept an exact version identifier;
  • restore and permanent exact-version deletion call the provider implementation.

The frontend never offers version controls for a bucket that failed the probe.

An object whose current version is a delete marker is not a live object. MinIO still lists its folder in a listing with a delimiter, and lists no key under it.

The listing therefore asks for one key under each folder of the page. This applies to a bucket with versioning on MinIO, or on a provider that the server does not know. It sends 4 requests at a time for 200 folders at most.

It removes the folders that have no key. A failed request keeps its folder. SeaweedFS, AWS and Garage do not list such a folder. The server sends no extra request to them.

Browser-only version comparison

The comparison is limited on purpose to two immutable versions of the same object key. The browser gets the exact sizes of the versions. It reads both versions with strict 2 MiB Range requests, compares the blocks and stops at the first byte that differs.

The backend has no generic comparison route and does not retain comparison state or content.

Large-object readers

Range-aware readers use exact start and end offsets, validate HTTP 206 and Content-Range, bind sessions to ETag/generation when available, and reject expanded or full-object responses.

Caches are LRU structures with a bound in bytes. Parsers read the indexes, headers, trailers and central directories of a format, and the members that they name. They do not collect complete objects.

Work on a complete object starts only after an explicit action, such as the integrity check of one object. It streams through small fixed buffers, under the background budgets of bytes and requests.

Archive extraction

ZIP-compatible archives use their central directory. A selected member is read from its exact compressed ranges, decompressed as a stream, and written directly to the explicit destination object.

The server never writes a temporary archive or member to disk. Stowr refuses unsafe paths, symbolic links, encrypted members, collisions, oversized expansion and destinations that already exist. It aborts an interrupted provider upload when the provider API has an abort.

Browser interface

The binary embeds one browser interface: the tree src/public/. The top of assets/css/stowr.css gives the design rules as tokens.

The tree contains these pages and scripts:

  • index.html is the browser page, preview.html the preview page, info.html the information page of an instance and 404.html the page of an unknown path.
  • assets/js/common/ has the shared scripts (API, previews, dialogs). preview.js is the preview page.
  • assets/js/app.js is the browser page. uploads.js is the bulk upload. tags.js and metadata.js are the sections of the details that edit the tags and the metadata. theme.js applies the theme before the first paint. session.js gives one message for an ended sign-in (401) or a server that does not answer.
  • assets/css/dialogs.css and assets/css/viewers.css have the rules for the dialogs and the previews. Each colour is a token of stowr.css, so these rules follow the theme.
  • assets/icons/tabler/ has one Tabler icon (MIT) for each name. assets/css/icons.css gives the icon for each mdi-* name of the shared scripts.
  • assets/vendor/ has the vendored libraries: PDF.js, highlight.js and marked. A unit test of the server makes sure that a page or a script loads each of them.

Frontend path model

Assets and API URLs are relative to document.baseURI. A path-stripping reverse proxy can therefore expose the same build at /, /stowr/, or another prefix without an HCL public-path setting or a frontend rebuild.
