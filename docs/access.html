This page comes from docs/ACCESS.md in the repository.

Stowr follows the ProcurAuth protocol for the access of people. A reference such as P 9.4 is a paragraph of this protocol. The text of this document is the behavior of the code. The generated list of the keys is in configuration-reference.md. The result of the conformance test is in CONFORMANCE.md.

Principle

The access policy has three parts:

  1. Authentication. The edge authenticates the person. The edge signs an identity token and puts it in a request header.
  2. Check of the token. Stowr checks the token on each request. The token gives the subject: the id of the person.
  3. Decision. Stowr asks a PDP (Policy Decision Point) for each operation. The PDP uses the AuthZEN Authorization API 1.0.

Stowr applies each decision on the server. The page of the browser shows or hides controls, but it never decides.

The edge and the PDP are outside Stowr. This document names no product for them. The edge and the PDP can be any programs that follow ProcurAuth.

The block and the two modes

The access block is mandatory. A file without it stops the start. Thus nobody gets the open mode by mistake. The key mode has two values.

ModeBehavior
authzenStowr checks the identity token and asks the PDP. The blocks identity and pdp are mandatory.
openStowr checks no token and asks no PDP. The two blocks stop the start. The route of the action document and the route of the options give 404.

The mode open is for a deployment where a reverse proxy that authenticates the users decides who can reach Stowr. In this mode, each request that reaches Stowr can do each operation that the process ceilings let. Stowr writes a warning at start.

configuration-reference.md gives each key with its default, its range and its forms. These items stop the start:

  • No access block, no mode, or a mode that is not authzen or open (lower case).
  • mode = "open" with an identity block or a pdp block.
  • mode = "authzen" without the identity block or the pdp block, or without a mandatory key.
  • A pdp.url with http:// and plain_http = false. A pdp.url with https:// and plain_http = true.
  • A pdp.token in clear text in the file. Use token_env or token_file.
  • usage_timeout that is less than timeout.
  • More than 256 bucket and volume blocks together, or a label of more than 256 bytes.
  • An action document of more than 64 KiB.

A full example for the mode authzen:

hcl
access {
  mode = "authzen"

  identity {
    header           = "X-Identity-Token"
    issuer           = "https://edge.example"
    audience         = "stowr"
    public_keys_file = "/run/keys/edge-jwks.json"
    max_age          = "5m"
    clock_skew       = "60s"
  }

  pdp {
    url             = "https://pdp.example:4182"
    token_file      = "/run/secrets/pdp-token"
    timeout         = "500ms"
    usage_timeout   = "6s"
    cache_ttl       = "30s"
    max_evaluations = 64
  }
}

An example for the mode open:

hcl
access {
  mode = "open"
}

A duration is one whole number and one unit: ms, s, m or h. For example: 500ms, 30s, 5m. A sign, a fraction or two units (1m30s) stops the start. clock_skew must be a whole number of seconds.

At start, Stowr writes a config.warning line in these cases:

  • mode = "open".
  • pdp.plain_http = true: Stowr sends the PDP token and the questions without TLS.
  • mode = "authzen" and server.listen has no host or a wildcard host (0.0.0.0, ::). Limit the network (refer to "The network rule").

The identity token

The token is a JWT that the edge signs. Stowr checks each request that is not exempt (refer to "Routes with no PDP question"). The rules:

  • The header alg is exactly Ed25519 or ES256. Stowr refuses EdDSA, none, HS256 and each other name.
  • The header typ is exactly JWT. Stowr refuses another value (for example at+jwt) and a token without typ.
  • The header kid selects the key. Stowr refuses an unknown kid, and a kid that belongs to a key of another algorithm. When the text of public_keys holds more than one key, Stowr refuses a token without kid. When it holds one key, a token without kid is checked with this key. Stowr never tries each key.
  • Stowr refuses a header crit, a duplicate member in the header or in the claims, and a token of more than 16384 bytes.
  • The claims iss, sub, aud, iat and exp are mandatory. iss must be the configured issuer. aud must be the id of the service, or an array that holds it.
  • sub has 1 to 256 bytes of UTF-8, without a control character. Stowr uses it as opaque text. It sends it to the PDP as the subject with the type user, and sends no other claim.
  • iat, exp and nbf are whole numbers of seconds since the Unix epoch (P 9.3). Each one is a JSON integer with digits only. Stowr refuses a fraction, an exponent and a sign, for example 1792569600.0, 1.7925696e9 and -1. It never rounds or converts such a value.
  • Stowr applies the clock skew to iat, exp and nbf. It refuses a token when its clock is later than exp plus the skew, and when iat is later than its clock plus the skew. The claim nbf is optional. When the token has nbf, Stowr refuses the token when nbf is later than its clock plus the skew.
  • Stowr refuses a token when exp is less than iat, or when exp minus iat is more than max_age.
  • Stowr ignores each unknown claim. It reads owner for the log only. It never uses owner for a decision.
  • Stowr reads the token only from the configured header. It never reads Authorization, a cookie or a query parameter. The header name must not be Cookie, Authorization, Host, Content-Type or Content-Length.
  • Two copies of the header are a refusal. The edge must replace the header (P 9.1).

Stowr keeps the result of a valid token until exp plus the skew. The key is the SHA-256 hash of the text of the token. The cache has 4096 entries. When it is full, Stowr drops the expired entries. When it is still full, Stowr keeps no new result.

A request with no valid token gets 401 unauthenticated. The body has no reason. For a request with an unsafe method, Stowr also sets Connection: close, so that it does not read the body. The log line access.unauthenticated gives the reason: missing, malformed, algorithm, type, kid, signature, issuer, audience, expired, not_yet_valid, max_age, subject or claims.

Public keys

access.identity.public_keys holds PEM text or a JWK Set (RFC 7517), with the rules below. Stowr reads the text as a JWK Set when it starts with { after spaces, tabs and line ends. Else it reads PEM.

  • PEM: 1 to 16 -----BEGIN PUBLIC KEY----- blocks. Each key is Ed25519 (Ed25519) or P-256 with an uncompressed point (ES256). Outside a block, a line must be empty. Other text, a PEM header, a private key and another type of key stop the start.
  • JWK Set: a JSON object with a keys array of 1 to 16 keys. A key of type OKP has crv Ed25519 and x (RFC 8037). A key of type EC has crv P-256, x and y (RFC 7518). The point of a P-256 key must be on the curve.
  • The alg of a JWK is optional. When it is present, it must be Ed25519 (or EdDSA) for OKP, and ES256 for EC. A token header with the alg EdDSA stays refused. The members use and key_ops have no effect.
  • A JWK with a private member (d, p, q, dp, dq, qi, oth or k), or with another kty or crv, stops the start. The JWK parser also refuses a duplicate member and data after the JSON object.

The kid of a key is the kid that the JWK declares: 1 to 256 bytes without a control character. A PEM key, or a JWK without kid, gets the RFC 7638 thumbprint of the key as kid. Two keys of a JWK Set cannot have the same kid. print-config shows each key as its type and its kid, for example ["Ed25519 kid=kPrK_qmxVWaYVA9wwBF6Iuo3vVzz7TxHCTwXBygrS4k"].

The network rule

Stowr must accept requests only through the edge (P 9.4). A client that reaches Stowr without the edge can use an identity token that it got, until the exp of the token. It then skips the other checks of the edge, for example the decision for the action access. The network rule stops this. Use a firewall, a network policy or a private network. Do not publish the listen address of Stowr.

The PDP token is a secret of Stowr. Keep the network of the PDP closed.

A false answer gives 403 forbidden with the action access. A PDP that gives no valid answer gives 503 pdp_unavailable. The action access never needs an approval (P 17.8): an answer with a reason of P 17.1 is not valid and gives 503 pdp_unavailable (P 10.1c). The action document never lists the action access. The resource tree

Stowr gives each request a node of this tree:

text
service   (access.identity.audience)
└── bucket       the label of a bucket block or of a volume block
    └── folder       the first part of the object key, below root_prefix
        └── subfolder    the second part of the object key

An object is not a node. The node of a key is the deepest folder that holds the key. A grant on a node covers each node below it. Stowr sends the node and the chain of its ancestors in resource.properties.ancestors (P 4.1). The chain comes from the configuration and from the key, never from a value that the client names.

The id of a bucket is the label of its block, not the name of the bucket at the provider. Two blocks have two nodes, also when they show one provider bucket. An id has 1 to 256 bytes of UTF-8, without a control character.

From a key to a node

The node comes from the exact relative key or prefix that the route sends to the storage. Stowr removes the / at the start and the NUL bytes. It does not clean the other parts: a part .. is an id like each other part.

The rule: cut the key at each /. Remove the last part. This part is the name of an object, or the empty part after the / at the end of a folder path. It can also be the incomplete last part of a list prefix.

The other parts are the folders, from the top. The walk stops at the depth of the tree. It also stops at the first part that cannot be an id. A walk that stops early gives a node nearer to the bucket. Thus a grant must be broader, never narrower.

The actions

The service publishes five actions. The document lists no action named access: this action opens the service to a subject (P 8.3). Stowr asks it only for the routes without data of a bucket.

ActionTypesWhat it lets a person do
object.readservice, bucket, folder, subfolderList, preview, inspect and download objects. Show versions, tags, metadata, retention, archive entries, the usage of a bucket, the lifecycle rules, the encryption and the incomplete uploads. Run Insights and the check of integrity. Download a ZIP of a folder.
object.writeservice, bucket, folder, subfolderUpload objects. Make folders. Restore versions. Change tags and metadata. Abort incomplete uploads. Be the destination of a copy, a move or an extraction.
object.deleteservice, bucket, folder, subfolderDelete objects, versions and folders. Be the source of a move or a rename.
object.lockservice, bucket, folder, subfolderSet or remove a legal hold. Set, extend or shorten the retention of an object version.
bucket.adminservice, bucketSave the lifecycle rules of a bucket.

The action document publishes an action only when the configuration serves it:

  • object.read needs one block with read in its permissions, or with no permissions key.
  • object.write needs one block with write, and object.delete needs one block with delete. A block with no permissions key gives both. Neither is published with server.access_mode = "force_read_only".
  • object.lock and bucket.admin need object.write published, and one bucket block with read and write. A volume has no Object Lock and no lifecycle rules.

The permissions of the blocks are the process ceiling (refer to "Order of the checks"). When the action of an operation is not published, Stowr answers 403 forbidden and asks the PDP nothing.

Limits

The document declares two limits:

The unit of a budget is a singular noun: the thing that one unit counts. The unit of a ceiling is a plural noun: the things that the value counts.

The PDP counts a budget. Stowr applies a ceiling. A grant gives a budget value only on the grant of the action access, which the edge decides. A grant gives a ceiling value on the grant of the action.

The action document

GET /.well-known/procurauth/actions gives the document. Stowr builds it one time at start, and gives the same bytes at each read. It needs no token and asks the PDP nothing. A bad token does not change the answer. The path /.well-known/access-actions has no alias: it needs the token and gives 404.

The document has the server (the id of the service), the types of the tree, the actions with their limits, and the limits. It has one resource for each bucket block and each volume block. A resource has the path bucket:<id> and the label. The label is the name of the block, when it has 1 to 60 characters. The document lists every bucket label. Thus a hidden bucket is not a secret.

Order of the checks

The handler of a route does these checks in this order:

  1. The middleware checks the identity token (401).
  2. The handler finds the instance. An unknown instance id gives 404 unknown_instance and no PDP question. The document already publishes each instance id.
  3. The handler checks the shape of the request: the body, the key, the prefix.
  4. The handler checks the process ceiling: the permissions of the block and server.access_mode. A refusal gives 403 permission_denied and no PDP question.
  5. The handler asks the PDP (authorize).
  6. The handler does the effect.

The decision of the PDP comes before the first byte of a body that Stowr reads, and before the first call to the storage.

The routes

Notation: N(key) and N(prefix) are the nodes of "From a key to a node". B is the bucket node. "Others" are the other permissions of the operation (P 5.5a). "Use" is the permission that the operation uses (P 5.5). A use with (usage) is an action that lists the budget writes: Stowr asks it with usage (refer to "Budget writes"). A permission that is not a use or an other is not asked.

Stowr asks the others first, in one request, with "context":{"permission_only":true} and without usage. Then it asks the use, in a separate request, without permission_only. The PDP ignores confirm for an other (P 17.8). Thus only the action of the use can need an approval.

  • an integrity check, and Insights.

A job keeps no subject. The permissions of the person who asks decide, at each request. A job whose permissions the PDP refuses answers 404 unknown_job, as a job that does not exist. A SQLite session whose permissions the PDP refuses answers 404 sqlite_session_not_found. A refusal of an upload continuation gives 403 or 429, and a PDP failure gives 503. A request for /api/stats asks its permission each time, also when it reuses a job.

Budget writes

The budget writes counts operations that change objects or bucket settings. The PDP holds the counter. Stowr asks one question for each use.

  • The use of an action that lists writes is one Access Evaluation with "context":{"usage":{"units":1}}. The context holds nothing else. The question is never part of a batch and never has the match subtree.
  • Stowr asks the Others first, with permission_only and without usage, in one batch when there are two or more. A refused Other gives 403 and no usage question. Then Stowr asks the use.
  • Stowr removes each repeated Other, and each Other that equals the use. Thus the same question without usage never comes before the question with usage (P 10.1).
  • The PDP takes the unit when it answers the question. Stowr takes the unit before the effect. A request that fails later (an unknown key, an error of the provider) has used its unit. Stowr never returns a unit.
  • An upload takes one unit when it starts. A job takes one unit when its route starts it. A chunk, a read of a job and a control of a job take none.
  • The process ceiling comes before the PDP. A request that the permissions of the block refuse takes no unit.

Approval of an effect

No route of Stowr can wait for the approval of an owner (P 17.7a). Stowr sends no context.approval and submits no approval request. The answer to the question of a use can have a reason of P 17.1: approval_required, approval_pending, approval_denied or approval_expired. Then Stowr answers HTTP 403 with exactly this body:

json
{"error":"approval_cannot_wait"}
  • This rule applies on each route that asks an action of the document, also on /s3 and /open/.
  • The operation has no effect, and Stowr keeps no such answer.
  • An other permission and the action access never get such a reason (P 5.5a, P 10.1c). Stowr reads such an answer as an answer that is not valid: 503 pdp_unavailable, and the line access.pdp_invalid_answer with the reason.
  • The read of the node of a listing (GET /api/list) is the use of the route: a reason of P 17.1 also gives this body.

The ceiling max_object_size

The PDP gives the ceiling in context.limits of a true answer. The value is a number of bytes. Stowr applies it to the part of the operation that the permission lets run. When two permissions of one operation give a value for one action, the lower value applies.

  • The value of object.read bounds each object that the operation reads. Examples: a GET of bytes, a range read for a preview, the source of a copy or a move, an archive.
  • The value of object.write bounds each object that the operation writes. Examples: a PUT, the destination of a copy or a move, a restored version, an extracted member, an upload.
  • A HEAD, a list, the tags and the reads of metadata have no check.

A size that is over the ceiling gives 403 with this body, before the first byte:

json
{"error":{"code":"ceiling_exceeded","action":"object.read","ceiling":"max_object_size","limit":1048576,"message":"..."}}

Stowr writes the line access.ceiling_refused. The body has no context.reason. Stowr never cuts an answer.

  • A ZIP of a folder, a copy or a move of a prefix, and an extraction check all the known sizes before the first effect.
  • A job keeps the ceilings of the request that made it. Its reads and controls do not change them.
  • When the size of an object is not known and a ceiling applies, Stowr refuses the operation.

A true answer with a ceiling name that the action does not list gives 403 forbidden (P 7.5). Stowr writes the line access.ceiling_unenforceable. A true answer with the name of a budget in context.limits is not valid: 503. Stowr ignores context.limits of a false answer. A value that is not a whole number of 0 or more is not valid: 503.

The options route

GET /.well-known/procurauth/resources lists the children of a node, page by page (P 5.6 to 5.8). It shows only the children that the subject can see. It needs the identity token. It has no action of its own.

Query parameters:

ParameterRule
typeMandatory. bucket, folder or subfolder. It must be the type of the children of parent.
parentAbsent for the buckets. Else a path such as bucket:b/folder:f. Each id is percent-encoded.
qA search text of 256 bytes at most. The rule depends on the type (refer below).
limitA whole number of digits from 1. A value above 50 gives 50.
afterThe cursor of the previous answer.

The rules of the query:

  • Stowr reads the raw query. It splits it at & and at the first =. It decodes each name and each value one time. It does not read + as a space. A bad percent-encoding gives 400 invalid_options_request.
  • A parameter that occurs two times gives 400. A request without type gives 400. A type that is not the type of the children of parent gives 400. A parameter that Stowr does not know is ignored.
  • The query has 16 KiB at most. A cursor that this route did not make for this type gives 400.
  • HEAD gives no body. Another method gives 405.

The answer has items and next. An item has id, label and has_children. An answer has 50 items at most. A label has 60 characters at most. next is null on the last page.

  • For the buckets, q is a substring of the id or of the label, without case. The items are sorted by the lower-case id. has_children is true. The cursor holds the last id that Stowr examined.
  • For the folders and the subfolders, q is a prefix of the id, with case. The storage can search only by prefix. A q with a / finds nothing. The children come from a list of the storage with the delimiter /, below root_prefix and the parent. The list uses the credentials of Stowr, and it reads at most max_scan_pages pages of 1000 keys. has_children is true for a folder and false for a subfolder.
  • A parent that does not exist, and a bucket whose permissions have no read, give no items. This is not an error.

For each child, Stowr asks the PDP one question with the match subtree and no usage. It asks object.read, object.write, object.delete, object.lock and bucket.admin, in this order. It asks only the actions that the document publishes for the type of the child. It stops at the first true answer. A child is visible when one answer is true.

One request asks at most 200 questions. When this bound stops the walk, the answer holds the items that Stowr found and a cursor. The answer can have no item and a cursor. A PDP that gives no valid answer gives 503 pdp_unavailable, never an empty list. The log line access.options gives the number of items and of questions.

Display rules

The interface shows what the person can do. These rules are for the display only. The server checks each operation (refer to "The routes").

  • GET /api/instances lists only the buckets where the person holds one action somewhere. For each bucket, Stowr asks the published actions on the bucket node with the match subtree. When the person holds object.read, object.write or object.delete nowhere in a bucket, the capability read, write or delete shows the source access. A question takes no unit. A PDP that gives no valid answer gives 503, never an empty list.
  • GET /api/list gives "access": {"read","write","delete"} for the node of the prefix. The interface uses it to hide the controls of upload and delete.
  • When the person cannot read the node but can read a deeper folder, GET /api/list gives a navigation list. It holds only the folders on the path to a folder that the person can read. Stowr removes the objects.
  • At the deepest level (a subfolder), such a request gets 403.
  • When the answer to object.read at the node has a reason of P 17.1, the request gets 403 with the body {"error":"approval_cannot_wait"}.

A match subtree never lets an operation run (P 4.4). The document publishes every bucket label. Thus a hidden bucket is not a secret.

Errors

The body of an error is {"error":{"code":"...","message":"..."}}. An access error also has action. The routes /s3 and /open/ answer the message as plain text with the same status. The one exception is approval_cannot_wait: its body is {"error":"approval_cannot_wait"} on each route.

StatusCodeCause

A PDP failure gives 503, never 403. The route fails closed. For the code pdp_unavailable, the page of the browser shows "The access decision service does not answer. Try again later." It does not show the notice of a server that does not answer.

The PDP client

Stowr uses the library procurauth-pep of ProcurAuth 1.1 for the check of the token, the questions to the PDP and the kept answers. Stowr asks each question with the AuthZEN Authorization API 1.0.

  • Stowr reads the metadata of the PDP at /.well-known/authzen-configuration at start, and writes the line access.pdp_metadata. A failure at start writes access.pdp_failed and does not stop the start. Stowr then reads the metadata before its next question. It reads the metadata again after one hour.
  • Stowr uses the endpoints of the metadata. When the PDP has no metadata (status 404, 405, 410 or 501), it uses the default paths /access/v1/evaluation and /access/v1/evaluations. An endpoint on another origin makes the metadata not valid.
  • Stowr reads the four members of the metadata: procurauth_usage_max_seconds, procurauth_idle_max_seconds, procurauth_evaluations_max_bytes and procurauth_evaluations_max_items.
  • Stowr sends the PDP token in Authorization: Bearer. It sends Content-Type, Accept and X-Request-ID. The request id is the X-Request-ID of the client when it has 1 to 128 safe characters. Else Stowr makes one.
  • One question is one Access Evaluation. Two or more questions without usage are Access Evaluations requests, with the subject at the top. A request has max_evaluations items at most and 1 MiB at most, and no more than the maxima of the metadata. Stowr splits a longer batch. After a split, each request is an Access Evaluations request, also a request with one item. Stowr asks a repeated question one time.
  • The questions of the others of an operation have context.permission_only equal to true. A question with permission_only never has usage.
  • The three questions of the member access of GET /api/list go in three requests, one after the other.
  • timeout is the deadline of a call without usage. One deadline covers all the requests of the call. The default of timeout is 500ms.
  • usage_timeout is the shortest wait for a question with usage. Stowr waits for the longer of usage_timeout and procurauth_usage_max_seconds plus 1 second. Thus Stowr always waits longer than the time that the PDP publishes (P 10.6). The default of usage_timeout is 6s.
  • Stowr never sends a question again, except when the request did not leave Stowr: no connection, or a connection that failed before the first byte. Then Stowr sends the request one more time.
  • When a request fails, Stowr sends no other request of the call. Each question of the call is then a failure, also a question with an answer in an earlier request of the call. An item of an Access Evaluations request that is not a valid answer makes the whole request fail.
  • The client follows no redirect, uses no proxy, and uses TLS 1.2 or newer. It trusts the certificate bundle of the image, as the provider client does. It reads at most 256 KiB of an answer. The connection timeout is 5 s, TLS handshake included, or less when the deadline of the call is nearer.
  • The client keeps at most 4 connections. It closes an idle connection after 5 s, or after half of procurauth_idle_max_seconds when this value is lower.
  • plain_http = true accepts an http URL. Use it only on a trusted network.
  • These cases are a failure: no answer before the deadline, a status other than 200, an invalid body, a wrong number of items. A status 401 or 403 of the PDP writes the line access.pdp_credential_refused.

The answer cache

cache_ttl is the longest life of a kept answer. The default is 30s. 0s keeps no answer. A revoked grant can stay active for cache_ttl at most.

  • The key is the subject, the action, the resource with its chain, the match, and the mark permission_only. Thus the answer to an other permission never serves the question of a use.
  • Stowr keeps the answers of the usage questions apart from the others.
  • Stowr keeps a true answer of a usage question only when units is 0. It keeps it for cache_ttl. A kept answer of this kind lets the use run without a question. Stowr never keeps a true answer with units of 1.
  • Stowr keeps a budget_exceeded answer of a usage question for the lower of retry_after and cache_ttl. A hit gives the seconds that remain to the end of the retry_after of the PDP, at least 1.
  • Stowr never keeps a failure, and never keeps an answer with a reason of P 17.1. A false answer to a usage question without budget_exceeded counted nothing: Stowr keeps it as the answer to the same question without usage.
  • A kept false answer to the same question without usage refuses a use with no question (P 10.1).
  • The two tables hold 16384 entries at most. When they are full, Stowr drops the expired entries. When they are still full, Stowr keeps no new answer.
  • A cache hit writes no access.decision line, unless server.log_mode is detailed.

What Stowr adds to the library

The library procurauth-pep gives the rules of a PEP. Stowr adds these rules around it:

  • The request id in X-Request-ID, the wait of a usage question, and one deadline for each call.
  • One question for each repeated question of a call.
  • The depth bound of 32 levels for the JSON of a token. The reason kid in the log, for a kid that belongs to a key of another algorithm.
  • The permission of each refusal: the library gives a refusal for the whole operation. Stowr finds the refused permission in the requests of the call, or in a copy of the kept answers. The answer of Stowr names this action.
  • The retry_after of a budget_exceeded answer to a question without usage. A continuation that gets it gives 429.

Volumes and symbolic links

A grant gives access to a folder by the key of the object, not by its real path. A symbolic link from one folder to another folder would let a person read the other folder.

With mode = "authzen", a volume follows no symbolic link in the path of a key. This rule applies to each link, also a link to a place inside the volume.

  • Each link in the path of a key stops the operation with 403 volume_link_refused.
  • The list of a folder shows such a link as an unreadable entry. A walk of a tree leaves it out.
  • Stowr opens the last part of a file for a read or a copy with O_NOFOLLOW.
  • Stowr resolves path and root_prefix one time at start. A link in them is not a link of a key.

With mode = "open", Stowr follows a link to a place inside the root, and refuses a link that leaves it. Stowr never makes a symbolic link. A process outside Stowr that changes a link between the check and the use of a path can race the check.

Rotate a key

  1. Add the new public key to the text of public_keys: a new PEM block, or a new key of the JWK Set with its kid. Keep the old key. Restart Stowr.
  2. Make the edge sign with the new key.
  3. Wait for max_age plus clock_skew: then each token that the old key signed is expired.
  4. Remove the old key from the text of public_keys. Restart Stowr.

Stowr reads the keys one time at start. A restart clears the cache of tokens.
